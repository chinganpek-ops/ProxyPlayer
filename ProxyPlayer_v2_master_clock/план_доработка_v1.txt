глобальные vs локальные индексы + оптимизации
Проблема (что было)

В v6 и первой версии v7 индексы чанков были глобальными (от 0 до общего количества чанков в файле). При переходе на LazyIndex с окном (например, 600 чанков из 45 000) возник конфликт:

    StreamScheduler выдавал глобальный индекс (например, чанк 22 550)

    ReaderStage пытался найти chunk_offsets[22550], но массив имел размер 600

    Результат: выход за границы, пустые чтения, ошибки демукса

Решение: локальные индексы

Шаг 1 — IndexWindow

    Все массивы в окне (chunk_offsets, chunk_sizes, audio_chunks, video_records) хранятся с индексами от 0 до N-1, где N — размер окна.

    Добавлено поле window_start_chunk для пересчёта при старте и seek.

Шаг 2 — StreamScheduler

    total_chunks теперь равен количеству чанков в окне (600), а не глобально (45 000).

    Все индексы внутри планировщика — локальные.

Шаг 3 — ChunkPipeline

    ReaderStage._chunk_bounds принимает локальный индекс — никаких вычитаний.

    DemuxerStage._demux принимает локальный chunk_idx и local_chunk = chunk_idx - window.chunk_range()[0] уже не нужен — индексы сразу локальные.

    VideoDecoderStage и AudioDecoderStage не зависят от индексов чанков — работают с пакетами.

Шаг 4 — PlaybackEngine

    При старте: local_chunk = (global_start_frame - window.window_start_frame) // 12

    При seek: SeekEngine строит новое окно, PlaybackEngine получает новое окно, вычисляет локальный чанк заново.

    При JKL: _fast_seek работает внутри текущего окна. Если выходит за границы — вызывает seek_absolute.

Шаг 5 — StreamController

    При инициализации окна передаёт в PlaybackEngine глобальный стартовый кадр, а PlaybackEngine сам вычисляет локальный чанк.

    При росте файла (_check_mmap_growth) обновляет окно через LazyIndex.expand_window, затем передаёт новые чанки в планировщик.

Оптимизации (последние исследования)

А. Кэширование _abs_offset

    В IndexWindow добавлено поле cached_offsets.

    При построении окна смещения вычисляются один раз через _abs_offset(video_slice).

    build_chunks_from_cached_offsets использует кэш, не вызывая _abs_offset повторно.

    При инкрементальном росте кэш дополняется только новыми записями.

Б. Предвычисленный индекс аудиочанков

    В audio_arr теперь нет np.searchsorted для каждого чанка.

    Вместо этого: chunk_indices = audio_arr['pts'] // SAMPLES_PER_CHUNK — один векторизованный проход.

    Построение чанков: прямой проход по массиву с распределением записей по chunk_indices.

    Сложность: O(N) вместо O(N log M), где N — количество аудиозаписей, M — количество чанков.

В. Векторизованный size2

    В build_audio_tracks и incremental_append_audio_tracks вместо цикла по всем записям используется np.where по каждой дорожке с векторным вычитанием массивов.

Итоговая схема индексации
text

Файл: глобальные чанки 0..44999
Окно: кадры 270000..277200 → чанки 22500..23100 (глобально)
                                    ↓
IndexWindow хранит локальные индексы 0..600
StreamScheduler оперирует локальными 0..600
ChunkPipeline использует локальные 0..600
PlaybackEngine переводит глобальный кадр в локальный чанк при старте/seek

При seek:

    SeekEngine строит новое окно (например, кадры 100000..107200)

    Старое окно удаляется

    PlaybackEngine вычисляет новый локальный стартовый чанк

    Конвейер перезапускается с локального чанка 0

    Никакой математики в рантайме, кроме одного деления при старте

Это финальная архитектура. Все изменения точечные, обратно совместимые, не ломают существующий API.
