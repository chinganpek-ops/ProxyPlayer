ProxyPlayer v1 — отчёт о проделанной работе
Что сделано (v1)

1. Полный рефакторинг архитектуры

    Код разделён на модульные пакеты: core/, pipeline/, index/, seek/, decode/, buffer/, output/, file_io/, config/, utils/, ui/

    Старая кодовая база v6 сохранена в legacy/ для обратной совместимости

    Удалены монолитные модули: player_controller.py (2000+ строк), chunk_reader.py, hybrid_seek.py

2. Новые компоненты

    LazyIndex (index/lazy_index.py) — оконный доступ к индексу без полной загрузки в память

    SeekEngine (seek/seek_engine.py) — асинхронный seek с отменой и двоичным поиском IDR

    ChunkPipeline (pipeline/chunk_pipeline.py) — трёхэтапный конвейер: Reader → Demuxer → VideoDecoder/AudioDecoder

    StreamScheduler (pipeline/stream_scheduler.py) — приоритетное планирование загрузки чанков с контролем заполнения буфера

    SyncManager (core/sync_manager.py) — выделенная синхронизация аудио/видео с коррекцией дрейфа

    PlaybackEngine (core/playback_engine.py) — движок воспроизведения с JKL-перемоткой

    StreamController (core/stream_controller.py) — фасад, заменяющий старый PlayerController

3. Оптимизации

    Предвычисление абсолютных смещений (кэширование _abs_offset)

    Предвычисленный индекс аудиочанков (chunk_indices = pts // SAMPLES_PER_CHUNK)

    Векторизованный расчёт size2 для аудиодорожек

    Локальные индексы чанков (без пересчёта на каждом шагу)

    Контроль заполнения буфера в планировщике

4. Сохранённый функционал v6

    Поле ввода таймкода (двойной клик)

    JKL-перемотка (x2, x4, x8)

    Live-старт (с конца файла)

    Менеджер окон с треем и HTTP-сервером

    Многопроцессный режим (до 6 плееров)

5. Тестирование

    Модульные тесты: adaptive_chunk, stream_scheduler

    Интеграционные тесты: seek_engine, playback_engine, stream_controller

    GUI-тест: 5 тестов (старт, таймкод, пауза, seek, JKL) — все пройдены

Текущая проблема (над чем работаем)

Запуск плеера через менеджер по ID

Сейчас плеер корректно работает при прямом запуске (python main.py file.mp4). Однако при запуске через менеджер (HTTP-запрос с ID) дочерний процесс плеера не может инициализироваться — зависает на этапе StreamController._ready.wait().

Корневая причина: менеджер запускает IndexBuilder, который блокирует зеркало .idx (файл в %APPDATA%). Когда дочерний плеер пытается получить доступ к тому же зеркалу через prepare_mirror, он ждёт снятия блокировки и не может продолжить.

Что уже сделано для исправления:

    Убран вызов _start_index_builder из _open_player_from_path

    Убран вызов _start_index_builder из конструктора менеджера

    Исправлен main.py для корректного определения, запущен ли плеер как управляемый

    Добавлен таймаут в PlayerWidget с диагностическим сообщением

Осталось решить:

    Дочерний процесс всё ещё зависает — нужно убедиться, что блокировка действительно снята

    Возможно, старые процессы IndexBuilder остались в памяти — требуется полная очистка

    После исправления проверить открытие по ID через open_by_id.py

После решения этой проблемы плеер будет полностью готов к использованию в production-окружении.
